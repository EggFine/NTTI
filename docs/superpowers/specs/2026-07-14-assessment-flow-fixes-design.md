# NTTI 测评流程修复设计

## 目标

以最小改动修复追加题无法收敛、追加题导致评分偏高、末题饮酒追问被跳过、语言切换丢失分享参数，以及分享载荷边界校验不足的问题。保持现有 UI、题库、人格类型和 Cloudflare 部署结构不变。

## 环境与约束

- 目标环境：Windows 11、Node.js 24、Next.js 16.2.3、React 19.2.4。
- 只使用 `package.json` 已有依赖；允许补充基于 Node.js 内置测试运行器的测试脚本，不引入测试框架。
- 不引入服务端签名、数据库或新的 API 路由。
- 修改应局限于评分、答题状态、语言切换和分享解码相关文件。

## 设计

### 1. 追加题收敛

`buildExtraQuestions` 接收已经追加过题目的维度集合。某个维度仅在以下条件同时满足时追加一道题：

1. 该维度尚未追加过；
2. 初始答案中至少有两个有效分数；
3. 最大值与最小值之差至少为 2；
4. 题库仍有未使用题目。

`TestApp` 维护已追加维度集合，并在重新开始测试时清空。一次追加轮次可以包含多个维度，但每个维度在整个测试中最多追加一道题，因此流程最多增加 15 道题，并在下一次完成回调中自然收敛。

### 2. 分数归一化

评分时同时记录每个维度的答案总和与有效答案数量。将任意题数的答案归一化到原三题量表：

`normalizedScore = round((sum / count) * 3)`

归一化结果限制在 3–9 后继续使用现有概率表。展示用 `rawScores` 改为归一化分数，使不同维度保持可比较；没有有效答案的维度按最低边界 3 处理，维持现有防御性行为。

### 3. 动态饮酒追问

`TestScreen` 在选择饮酒入口题时先同步构造 `nextQuestions` 和 `nextAnswers`，再用同一份快照更新状态、决定下一题并调用 `onComplete`。这样即使入口题位于最后一位，新增追问题仍会成为下一题，不会提交旧题目列表。

### 4. 语言切换

`LanguageSwitcher` 在点击时读取 `window.location.search`，并通过纯函数构造目标 URL。切换语言时只替换路径中的语言前缀，并原样保留所有查询参数；无查询参数时不添加多余问号。该方案避免 `useSearchParams` 在静态路由中引入额外的 `Suspense` 边界。

### 5. 分享载荷校验

保留当前客户端校验和以检测链接损坏，但不把它视为安全签名。解码时增加以下限制：

- `typeCode` 必须是非空、长度受限的字符串；
- `similarity` 必须是 0–100 的有限整数；
- `exact` 必须是 0–15 的有限整数；
- `special` 标志只能是 0 或 1；
- 15 个维度字符只能是 `L`、`M`、`H`。

人格代码是否存在仍由 `reconstructFromShare` 根据当前语言数据验证。此次不改变 URL 格式，已有合法分享链接继续可用。

## 测试策略

使用 Node.js 内置 `node:test` 与 `node:assert/strict`，通过 TypeScript 编译后的测试产物运行，不增加第三方依赖。至少覆盖：

1. 不一致维度只追加一次；多个不一致维度各追加一次；已追加维度不会再次追加。
2. 三题评分保持原结果；四题及更多低分不会因题数增加变成高等级；高分同理保持稳定。
3. 饮酒入口位于最后时选择触发选项会进入追问题；非触发选项正常完成。
4. 语言切换保留分享查询参数和普通查询参数。
5. 分享解码拒绝越界、非整数及非法特殊标志，同时接受现有合法载荷。

## 风险控制

- 评分公式变化是最高风险点，因此先用纯函数测试锁定边界，再修改实现。
- 动态题目状态使用单一快照，避免 React 异步状态造成的新竞态。
- URL 拼接提取为纯函数测试，组件仅负责读取浏览器状态和执行跳转。
- 完成后运行测试、ESLint、TypeScript 检查和生产构建；若依赖环境仍缺失，明确报告未执行项，不宣称验证通过。
